# GPU audit, 19 September 2026

This audit covers all ten production shaders and their shared height-sampling include. It preserves rendering resolution, texture/map resolution, floating-point formats, lighting, visibility tests, winter features and stereo paths. It does not establish that every low-end device can run the game or predict a live FPS increase.

## Accepted change

`SnowVehicle.shader`, accumulation pass 3, previously read four world-height samples separately for its shelter calculation. It now reuses the existing `SnowHeightSampling.cginc` implementation: D3D11 gathers the same four texels, compares each height separately, then interpolates the resulting visibility. The fallback on other backends retains four texture reads. Explicit branches select the near, far or distant map.

The meaning of shelter, previous snow, snowfall increments, map boundaries and empty capture texels remains unchanged. Map resolution remains 1024 × 1024; vehicle height/snow layers remain 256 × 256. The vehicle render/data, exclusion, instancing, coal and rail-erasure passes are unchanged.

The source shader passed 216 reference comparisons, covering 14,155,776 RGBA pixels, with maximum component difference **0** (`full-opt-snow-accumulation-source2.log`). The comparison uses the complete pre-edit shader retained as an Editor-only reference. Cases cover empty/sparse/dense captures, initial/restored masks, zero/positive accumulation, map transitions, rotation and floating-origin offsets.

The Unity AssetBundle rebuild completed. Packed stereo-program verification passed, and all three runtime bundles were repacked to LZMA. The packed accumulation run also completed successfully: **216 scenarios, 14,155,776 pixels, maximum component difference 0**, followed by all six throughput workloads. No stereo shader source was changed. The packed result is recorded in `artifacts/verification/full-opt-snow-accumulation-packed.log`.

An additional early-return proposal for empty capture texels was rejected. It changed a restored-mask result in the sparse, zero-accumulation case by 0.001953125. Removing that early return restored exact parity. The test tolerance was not increased to accept this difference.

## Measurement limits

The earlier 2560 × 1440 full-screen experiment measured incremental full-minus-copy medians of approximately 0.127–0.267 ms for its prepared scenes. Those are CPU submission plus GPU-completion measurements, not isolated GPU timestamps or a live yard bottleneck diagnosis. No further reduction in screen resolution, exposure resolution or snow detail follows from that experiment.

The accumulation benchmark compares the new shader with the pre-edit reference over identical GPU resources and alternates execution order. It includes CPU command submission and a completion readback, reports raw medians and per-capture normalization, and must not be presented as game FPS. The runtime updates at most one vehicle mask per frame, so even a large relative improvement in this isolated pass can have a small total-frame effect.

The packed benchmark used 128 captures per batch, a production-format 256 × 256 RHalf target, 1024 × 1024 RFloat shelter maps, and seven alternating trials per workload. The measured medians were:

| Capture/map | Reference batch, ms | Gather batch, ms | Reference/capture, µs | Gather/capture, µs | Time reduction |
| --- | ---: | ---: | ---: | ---: | ---: |
| Sparse / near | 0.8366 | 0.5880 | 6.536 | 4.594 | 29.7% |
| Sparse / far | 0.8791 | 0.6773 | 6.868 | 5.291 | 23.0% |
| Sparse / distant | 0.8439 | 0.5453 | 6.593 | 4.260 | 35.4% |
| Dense / near | 0.7358 | 0.4924 | 5.748 | 3.847 | 33.1% |
| Dense / far | 0.6420 | 0.4755 | 5.016 | 3.715 | 25.9% |
| Dense / distant | 0.6415 | 0.5674 | 5.012 | 4.433 | 11.5% |

All six synthetic workloads improved, with exact output parity. The absolute saving was approximately **0.58–2.33 µs per capture** in this cached-resource test. This validates retaining the equivalent shader change, while also showing why it should not be described as a large live FPS improvement by itself.

## Separate memory consideration

The runtime's 256 × 256 vehicle arrays use RFloat height and RHalf snow layers: approximately 384 KiB per slot, or 96 MiB at a capacity of 256 slots, excluding temporary targets and other textures. A future resident-map cache could reduce peak GPU memory, but would need reliable mask preservation and restoration for newly visible vehicles. Silently reducing map resolution or dropping accumulated state would not meet this audit's preservation requirement.

The bounded follow-up memory review found the straightforward reductions already present: RHalf snow, separate R8 slope, ARGBHalf surface IDs/coordinates, compact half-resolution HDR AO, temporary render-target release after rendering, shared/reused coal blends, lazy profile creation and bounded concurrent seasonal readbacks. Persistent vehicle arrays intentionally retain state while winter coverage remains; changing residency cannot be treated as a texture-format-only edit.

Two further functionally equivalent approaches merit separate verification, rather than inclusion in this iteration:

- Generated fallback terrain layers are constructed as readable `Texture2D` objects and then filled through `Graphics.CopyTexture`. Releasing their CPU backing **before** the GPU copy could save CPU memory because their consumer needs a sampled GPU texture. Calling `Apply` after the copy would risk replacing copied pixels with stale CPU data, so this needs direct output and later-consumer tests first. Ordinary packed profile textures must remain readable because the repository deliberately reads prepared mip pixels from the CPU to avoid GPU stalls.
- A saved vehicle snow mask uses 128 KiB of raw bytes, and after saving may also retain its compressed Base64 form. Inactive mask records could be compressed and release their raw copy through a bounded work queue, retaining restoration and save semantics. Compression time, concurrent readback callbacks and repeated despawn/respawn would need explicit testing. Dropping raw state without a valid packed form is unacceptable.

Neither proposal was implemented here. The established resource and mask lifetime rules remain unchanged; an unmeasured residency rewrite would add risk without a demonstrated frame-time benefit.

## Rejected CPU culling experiment

A prepared managed frustum candidate passed 803,719 exact comparisons against Unity, including boundary and stereo cases. However, seven alternating million-box trials per workload measured it **3.03–3.81 times slower** than Unity's native `GeometryUtility.TestPlanesAABB`, across mono/stereo and inside/outside/mixed distributions. The candidate was therefore removed from production. `SnowCullingOptimizationVerification` retains the candidate as Editor-only reproducible evidence; it adds no runtime path or setting.

The original measured log is `artifacts/verification/full-opt-culling-micro.log`. This result is a warning against assuming that fewer managed/native calls automatically mean less CPU time: native optimized math won decisively for these tests.

A separate renderer-native-visibility experiment was also rejected and is **not shipped**. Its final verification passed 1,475 checks, but all three benchmark cases retained 582 visible renderers and culled none; measured CPU recording increased by approximately 1–9%. The candidate is archived as experimental evidence rather than enabled as a runtime optimization. See `artifacts/verification/full-opt-native-visibility-final.log`.
